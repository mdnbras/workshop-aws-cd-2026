Fundamentos

Síncrono é simples. Assíncrono desacopla tempo.

Comunicação síncrona

API A chama API B e espera. O tempo e a disponibilidade de B entram no caminho crítico.

API A
→
API B
VS
Comunicação assíncrona

O producer registra/publica o fato. O processamento pode acontecer depois, no ritmo do consumer.

→
B

Fundamentos
Um evento não é “faça isso”.
É “isso aconteceu”.
OrderCreated

Um pedido foi criado.

PaymentApproved

Um pagamento foi aprovado.

UserRegistered

Um usuário foi cadastrado.

Eventos bons descrevem fatos do domínio no passado e carregam apenas o necessário para os consumidores.
Evite entrar em Event Sourcing. Foque em nomenclatura e significado do evento.

Kotlin

O código foi separado para ficar didático.

api/

HTTP e DTOs.

application/

Caso de uso de criação.

domain/

Evento `OrderCreated`.

messaging/

Contrato + publisher SNS.

O controller não precisa conhecer detalhes do AWS SDK.
Mostre o fluxo Controller → Service → Publisher, sem entrar em DDD profundo.
OrderCreated

Nosso contrato de evento.

data class OrderCreated( val eventId: UUID, val orderId: UUID, val customerEmail: String, val total: BigDecimal, val occurredAt: Instant )
eventId

Identidade do evento. Útil para rastreamento e idempotência.

occurredAt

Quando o fato aconteceu — não quando o consumer recebeu.

Pergunte quais campos notification e analytics realmente precisam.
Producer

O producer publica o fato e segue adiante.

snsClient.publish( PublishRequest.builder() .topicArn(topicArn) .message(message) .build() )
O producer conhece o tópico. Ele não precisa conhecer quantos consumidores existem.
Este é o ponto para verbalizar “desacoplamento organizacional e técnico”.
Hands-on

SQS Consumer

Receber → processar → apagar.

1. Receive

O worker faz polling na fila.

2. Process

Executa a ação da aplicação.

3. Delete

Remove a mensagem somente após sucesso.

Se der erro antes do delete, a mensagem pode reaparecer depois do Visibility Timeout.
Esse slide prepara o raciocínio para retry no Lab 5.
Entrega

Visibility Timeout é um empréstimo temporário da mensagem.

Mensagem visível
→
Consumer recebe
→
Fica invisível
Sucesso → delete
Falha → timeout expira → retry
Evite termos muito formais. Diga: “o SQS dá a mensagem para um worker por um período; se ele não confirmar, ela volta”.
Importante
Uma mensagem pode ser entregue mais de uma vez.
At-least-once

Seu código não deve presumir “uma única entrega”.

Idempotência

Processar a mesma mensagem novamente não deve duplicar efeito de negócio.

Não vamos implementar idempotência completa em 2h — mas você precisa sair sabendo por que ela existe.
Use exemplo: cobrança duplicada ou e-mail duplicado. Não aprofunde em locking.

Demo

Uma mensagem ruim. Dois resultados diferentes.

curl -X POST http://localhost:8080/orders \ -H 'Content-Type: application/json' \ -d '{"customerEmail":"fail@workshop.local","total":99.90}'
analytics-worker

Processa normalmente.

notification-worker

Falha, recebe novamente e depois encaminha para DLQ.

Abra dois terminais com logs lado a lado para deixar a independência visível.
Resiliência

Retry infinito transforma uma mensagem ruim em incidente permanente.

CPU

Consome recursos repetidamente.

Logs

Gera ruído operacional.

Fila

Pode atrasar trabalho útil.

Diagnóstico

Esconde uma falha definitiva.

A DLQ tira a mensagem problemática do fluxo normal para investigação controlada.
Faça a analogia de separar um item defeituoso na linha de produção.
